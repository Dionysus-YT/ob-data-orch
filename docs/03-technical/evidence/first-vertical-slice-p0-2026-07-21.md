## 4. OBDUMPER 运行发现

### 4.1 Windows 本地库发现

首次运行在连接数据库后报错：

```text
org.apache.hadoop.io.nativeio.NativeIO$Windows.access0(Ljava/lang/String;I)Z
```

工具包包含 `hadoop.dll` 和 `winutils.exe`，但 Windows 启动脚本没有把其目录加入本地库搜索路径。首次验证通过进程级路径补充绕过该问题。

用户随后配置了用户级 `HADOOP_HOME` 和 `%HADOOP_HOME%\bin`。2026-07-21 10:38 刷新进程环境后复测，`NativeIO$Windows.access0` 不再出现，确认本地库问题已经修复。工具能够完成连接、表元数据查询、任务拆分并进入 CSV 写入阶段。

### 4.2 Windows 绝对路径格式

分别验证了默认嵌套输出、`--no-nested-dir` 和标准 `file:///E:/...` 输入，工具最终都构造出以下错误路径：

```text
file://nullE:/...
```

错误发生在 CSV 文件创建阶段，不是连接、认证、表不存在或磁盘空间不足。OceanBase 官方文档将 `-f/--file-path` 定义为本地磁盘绝对路径。用户随后确认 4.3.5 在 Windows 下可以直接识别以下实际参数格式并成功导出：

```text
--file-path "E:\workespace\ob-data-orch\tmp\p0-validation\run-06\output-test"
```

因此产品基线采用用户填写的完整 Windows 绝对路径作为实际参数，不再引入工作目录拆分或相对路径转换。前述 `file://null` 结果继续保留为自动化环境差异，需要在正式 Agent 环境回归，但不改变路径参数格式。

该绝对目录已存在一份成功导出，CSV 与 run-09/run-10 的行列数、字节数和 SHA-256 一致。

该目录已有导出内容，再次作为同一输出目录运行时，OBDUMPER 会以“输出目录非空”拒绝执行。平台不自动改写用户填写的路径，也不自动追加子目录或增加 `--skip-check-dir`；预检查发现目标非空时直接阻断，由用户填写新的完整任务路径或明确处理已有内容。

### 4.3 退出码不可信

多次工具日志均记录 `System exit 1`，但 `obdumper.bat` 返回 0。Agent 必须结合受控 Java 进程、工具终态日志、结果文件和任务事实判断结果，不能只读取批处理退出码。
