# 日志流重组与脱敏最小验证

> 验证日期：2026-07-21
> 验证环境：Windows AMD64、Go 1.26.4
> 结论：记录边界重组、双层幂等脱敏和批次摘要候选可行；正式采集协议与跨平台运行仍待实现验证

## 1. 目的与边界

本次验证只回答三个实现前问题：

1. 当密码或 UTF-8 字符跨越操作系统管道读取块时，能否在持久化前完整重组并脱敏；
2. Agent 与控制面使用相同固定掩码重复处理时，结果能否保持稳定；
3. 同一批日志的重发能否通过摘要幂等识别，而相同序号不同内容能否被拒绝。

验证程序和结果位于 Git 忽略的 `tmp/log-contract-spike/`，只使用运行时随机合成秘密和合成组合用户名，不读取真实数据库凭据，不属于正式业务代码。

## 2. 已有 OBDUMPER 日志事实

对 `tmp/p0-validation/` 中已有 10 份 `ob-loader-dumper.info` 做了不输出正文的只读统计：

- 文件大小为 396～11,548 字节；
- 每份 5～113 个非空物理行；
- 只有部分物理行带可识别的时间/级别前缀，说明异常、列表或堆栈会形成续行；
- Windows 文件使用 CRLF；
- 10 份文件均包含完整组合用户名；
- 未发现此前测试密码原值。

因此不能简单地把“每次 Read 返回值”或“每个物理行”都当作完整产品日志记录，也不能原样上传工具文件。

## 3. 合成验证方法

验证输入包含：

- 一个随机生成且不输出的合成密码；
- 一个合成组合用户名；
- 中文 UTF-8 文本；
- 密码与中文字符都被故意切在两个读取块之间；
- 一个超过 256 KiB 且没有及时换行的异常记录；
- 同一流和序号范围的重复批次及冲突批次。

处理顺序为：

```text
读取任意字节块
→ 按来源维护内存重组缓冲
→ 得到完整记录或确认超限
→ Agent 第一层固定掩码脱敏
→ 控制面第二层相同规则再次脱敏
→ 生成带来源和序号的 JSONL 记录
→ 计算流、序号范围和内容摘要
→ 写入临时脱敏段文件
```

超长记录不会把原文持久化；采集器丢弃到下一个安全记录边界，并生成不含原文的缺口记录。

## 4. 验证结果

| 项目 | 结果 |
|---|---|
| 密码跨两个读取块 | 已按记录边界重组 |
| UTF-8 字符跨两个读取块 | 重组后仍为有效中文 |
| 段文件包含合成密码 | 否 |
| 段文件包含合成组合用户名 | 否 |
| Agent/控制面重复脱敏 | 结果幂等 |
| 同一批次重复摘要 | 相同，可安全确认重发 |
| 相同序号范围、不同内容 | 摘要不同，应判冲突 |
| 超过 256 KiB 的无边界记录 | 原文不保存，生成显式缺口 |

本次脱敏段文件为 309 字节，SHA-256：

```text
12f8533b5e2b390d5025e09b359face35cc5c53b3eb8024e457696dc544c5d93
```

该摘要只标识本次随机合成验证产物，不是正式日志格式或发布摘要。

## 5. 得到的设计约束

- 脱敏必须在记录重组之后、首次持久化之前完成；
- 不允许直接逐 Read 块替换字符串，否则跨块秘密会泄露；
- 每个来源必须有独立缓冲、序号和重连状态，不能把 stdout、stderr 和工具文件混成一个流；
- 超长或无法安全解析的记录采用失败关闭：不保存原文，显式产生缺口；
- 双层脱敏必须使用同一策略版本和固定掩码，不允许第二层恢复或改变第一层掩码；
- 批次幂等必须同时绑定来源流、序号范围和内容摘要；只看 requestId 或序号不足以发现冲突；
- 组合用户名属于标识敏感信息，需要与密码不同的分类，但普通日志同样不得保留完整值。
